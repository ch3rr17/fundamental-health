# AI Donor Outreach Agent — PRD

## Problem Statement

Someone at FundaMental Health currently has to manually research each Apollo-generated prospect and hand-pick/personalize the right talk track before anything goes into Klaviyo, across 5 talk-track segments (community donors, nonprofit/marketing professionals, board prospects, financial institutions/CRA, DAF advisors & giving circles). That manual step is the bottleneck between Apollo's segmented prospect list and Klaviyo's touchpoint sequences, and it doesn't scale past a handful of prospects at a time.

## Solution

A local web app that bridges Apollo and Klaviyo for the Development Associate / Fundraising Intern: pulls the Apollo-generated, segmented prospect list via live API (or CSV import as a first-class fallback, seeded by the 123-prospect fixture set), checks each prospect against Klaviyo and Monday.com for prior contact (matched on email, name+org fallback) and routes matches to a visible, overridable already-contacted bucket instead of the review queue, assigns a talk-track segment to unmatched prospects (rule-based and/or AI-inferred with a confidence indicator, with an explicit "unassigned — needs manual tag" state), has AI research each prospect and draft a talk-track-matched personalized email using only approved sources (Apollo prospect record, public professional profiles, org websites, public news/nonprofit affiliations) with no fabrication, puts the draft in a review queue for the intern to edit and approve, pushes the approved profile to Klaviyo (create/update + add to the matching talk-track-specific list) once approved, confirms send via Events API polling with a bounded timeout, and on confirmed send logs the prospect as a tracked item on the team's existing Monday.com board.

## User Stories

1. As a Development Associate/Fundraising Intern, I want the app to pull the Apollo-generated segmented prospect list automatically, so that I don't have to manually copy prospects out of Apollo.
2. As a Development Associate/Fundraising Intern, I want to import prospects from a CSV when live Apollo access isn't available, so that a platform-tier blocker on Apollo doesn't stop me from working the list.
3. As a Development Associate/Fundraising Intern, I want prospects who already appear in Klaviyo or Monday.com (by email, or name+org when email is missing) automatically routed to a visible "already contacted" bucket instead of the review queue, so that I don't re-research or re-approach someone we've already reached.
4. As a Development Associate/Fundraising Intern, I want to still be able to consciously pull someone out of the already-contacted bucket and re-approach them, so that the dedup check doesn't silently block a legitimate re-engagement.
5. As a Development Associate/Fundraising Intern, I want each new prospect automatically assigned to one of the 5 talk-track segments (with a confidence indicator), so that I don't have to manually decide which messaging category fits.
6. As a Development Associate/Fundraising Intern, I want prospects the app can't confidently assign a segment to flagged as "unassigned — needs manual tag" in the review queue, so that low-confidence assignments get a human decision instead of a silent guess.
7. As a Development Associate/Fundraising Intern, I want the app to research each prospect using only approved sources (Apollo record, public professional profiles, org site, public news/nonprofit affiliations) and draft a personalized, talk-track-matched email, so that I start from a strong draft instead of a blank page.
8. As a Development Associate/Fundraising Intern, I want the AI to omit uncertain details rather than invent them, and to show a confidence indicator on research findings, so that I can trust what's in front of me and know what to double-check.
9. As a Development Associate/Fundraising Intern, I want every AI-drafted email to sit in a review queue where I can edit or approve it, so that nothing goes out without a human checking it first.
10. As a Development Associate/Fundraising Intern, I want no draft to reach Klaviyo without my explicit approval, so that the human-in-the-loop requirement is actually enforced, not just a UI suggestion.
11. As a Development Associate/Fundraising Intern, I want approving a draft to create/update the prospect's Klaviyo profile and add them to the correct talk-track list, so that Klaviyo's existing list-triggered flow automation takes over sending without me doing anything else.
12. As a Development Associate/Fundraising Intern, I want to see a "confirming send…" state after I approve and push, so that the app doesn't look stalled or broken while it waits on Klaviyo.
13. As a Development Associate/Fundraising Intern, I want to see a clear fallback state ("pushed, send unconfirmed — check Klaviyo") if send confirmation times out, so that I know the push succeeded even if I can't get a firm send confirmation right away.
14. As a Development Associate/Fundraising Intern, I want a Monday.com tracking item created automatically once send is confirmed, so that the prospect shows up on the team's existing board without me copying it over by hand.
15. As a Director of Development / Executive Director / Major Gifts Officer, I want the app's output to land in the same Klaviyo lists and Monday.com board the team already uses, so that this new tool doesn't require standing up parallel tracking systems.
16. As a Director of Development, I want Apollo's own AI sequencing switched off for prospects this app handles, so that the same prospect doesn't receive duplicate or conflicting outreach from two systems at once.

## Implementation Decisions

- **Two prospect-ingestion paths, both first-class**: live Apollo API pull, and CSV import seeded by the 123-prospect fixture set at `docs/supporters/fixtures/segment-0{1-5}-*.md`. CSV import is not a degraded fallback bolted on later — it's architected in from day one because Apollo's "advanced API access" appears gated to its paid Organization tier (3-seat minimum) on some sources, and Apollo's Free-tier exports are capped at 10/month, either of which could otherwise block the whole demo on a platform-tier issue outside the team's control. Rejected: treating the live Apollo pull as a hard blocker with no fallback.
- **Segment assignment is an explicit app-side step**, not something pulled from Apollo — confirmed Apollo's data model does not tag prospects with a talk-track segment. Assignment is rule-based and/or AI-inferred with a confidence indicator, and prospects that can't be confidently assigned land in an explicit "unassigned — needs manual tag" state visible in the review queue, not silently dropped or guessed. This applies equally to the CSV path, since a CSV export carries no segment tag either.
- **Apollo's built-in AI email sequencing is switched off** for prospects this app handles (an operational/account-config step, not something the app enforces in code) — talk tracks live only inside the app now. Rejected: leaving Apollo's sequencing running in parallel, which risks duplicate/conflicting outreach to the same prospect from two systems.
- **Direct REST/GraphQL integration** with Apollo, Klaviyo, and Monday.com — no Composio layer, despite all three apps existing in the local Composio catalog. Rejected: Composio's pre-built actions, since going through Composio adds its own CLI install and auth-connection setup on top of native credentials, with no benefit at just three well-documented platforms.
- **Klaviyo push = profile create/update (`POST /api/profiles` → `201`) + add to a talk-track-specific list (`POST /api/lists/{id}/relationships/profiles` → `204`)**, one of 5 lists mapped to the 5 talk-track segments, relying on Klaviyo's native list-triggered flow automation to actually send. The app never triggers a flow by ID directly. Rejected: explicit per-talk-track flow-ID triggering, which adds a 5-flow-ID mapping/testing step with no functional benefit over list-triggered automation (Klaviyo's standard pattern). From the app's perspective this action is a "push," never a "send" — sending is entirely Klaviyo's flow automation, outside the app's control.
- **Confirmed-send verification via Events API polling, not webhooks** — Klaviyo's real-time webhooks (delivered/opened/clicked) are gated to Advanced KDP customers and registered app partners, unavailable on a demo account. The app instead polls `GET /api/events` filtered by `profile_id` for the account's "sent"/"received" metric, with a bounded timeout (e.g. 30-60s) and a "confirming send…" UI state while it waits. On timeout, surface "pushed, send unconfirmed — check Klaviyo" rather than blocking indefinitely. This supersedes an earlier decision to gate Monday.com sync on Klaviyo API-call success alone (ADR-0001, superseded by ADR-0002). **Blocking prerequisite**: the live demo Klaviyo account's actual "sent"/"received" metric ID must be identified before this can be built — it can't be determined from documentation alone.
- **Monday.com sync gates on confirmed send**, not just on the Klaviyo push API calls succeeding. It is a required live-demo integration, not a stretch goal. The item is created on the team's existing Monday.com board — the specific board ID and column mapping (name/org/segment/status) are still needed (see Further Notes) before this step can be built correctly. Monday.com auth is a personal API token against its GraphQL API (`api.monday.com/v2`); most sources indicate Free-tier accounts include raw developer API access (the "no automations/integrations" language appears to refer to Monday's no-code integration recipes, not the API itself), but this needs a 2-minute live confirmation (one test `create_item` mutation) before build.
- **Duplicate-contact check against both Klaviyo and Monday.com, matched on email address** (name+org as a weaker fallback when email is missing). Runs twice: once at import time, before AI research/drafting starts (so research effort isn't spent on someone who shouldn't be re-approached), and again as a cheap final guard immediately before the Klaviyo push, to catch races (two people running the app, or a prospect processed in a prior session). A match routes the prospect to a visible already-contacted bucket (showing prior contact date/talk-track when known) rather than the review queue or a silent drop. Default behavior is skip, not "ask every time" — but the intern can consciously override and re-approach from that bucket.
- **Human-in-the-loop review is a single, hard-required approval checkpoint** — one `draft.approved == true` gate immediately before the Klaviyo-push function runs, rather than review logic scattered through the pipeline. This is deliberate: a future release may let the team turn approval off entirely, and a single clean checkpoint means that's a toggle, not a re-architecture. The toggle itself is out of scope for this build (see Out of Scope) — approval stays hardcoded on.
- **AI Behavior Spec** (carried forward from the team's existing informal PRD, confirmed as still governing): human-in-the-loop required before any Klaviyo push; no fabrication (the AI omits uncertain details rather than speculating); confidence indicators shown on research findings; approved sources only — Apollo prospect records, public professional profiles, org websites, and public news/nonprofit affiliations.
- Terminology for this build follows the project's `CONTEXT.md`: prospect (pre-push) vs. profile/item (post-push); talk-track segment (assigned by the app) vs. talk track (the messaging content itself); review queue; push (app→Klaviyo) vs. send (Klaviyo's own flow automation, never something the app claims to do); already-contacted bucket (visible and overridable, not a silent block).

## Testing Decisions

No automated test seams are in scope for this build. Given the one-day hackathon timeline, the team decided correctness is verified through manual run-throughs of the live demo path (Apollo/CSV pull → dedup check → segment assignment → draft → approve → Klaviyo push → confirmed send → Monday.com sync) rather than through an automated test suite.

## Out of Scope

- Auto-send without intern approval.
- Follow-up sequences beyond the initial talk-track-matched outreach.
- Phone calls.
- Donation negotiation.
- Advanced CRM automation.
- Grant-proposal generation (tracked separately under the Grant Scoping Tool track).
- Apollo's own built-in AI email sequencing / talk-track-as-context-block usage (explicitly switched off for prospects this app handles).
- Real-time send/delivery confirmation via Klaviyo webhooks (tier-gated, unavailable on the demo account) — confirmed send uses Events API polling instead.
- Composio as the integration layer for Apollo, Klaviyo, or Monday.com.
- Explicit per-talk-track Klaviyo flow-ID triggering by the app (list-triggered flow automation is used instead).
- A settings toggle for turning human-in-the-loop review on/off — the approval gate stays hard-required and hardcoded on for this build; only the single-checkpoint design anticipates a future toggle.
- Automated testing (see Testing Decisions).
